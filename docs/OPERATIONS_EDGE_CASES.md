# Nine things that go wrong in deployment, and what this build does

Not features: behaviour under the conditions a running system meets. Each answer names the
mechanism in code and, where the build only has part of an answer, says so. Labels as in
`docs/ASSUMPTIONS.md`: **built** runs here and is tested; **partial** runs with a named gap;
**gap** is a documented next step, not a claim.

| #   | Condition                                                          | Answer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Status                                                                        |
| --- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1   | A user loses authorization while an approval is open               | The approval is checked at the click, not at the proposal. `ProposalsService.approve` re-reads the actor's role against the kind's approver (`can(actor, 'write', spec.approver)`) inside the deciding transaction; a role that no longer qualifies gets 403 and the row stays `PROPOSED`. The per-request HS256 token lives 2 minutes and is minted from the session by the web app, so a revoked session cannot mint another. What is **not** re-read at the click is the user row itself: a session whose user was deleted or demoted in the database keeps its role claim until the session ends (`JwtAuthGuard` trusts the claim; only `AskService.ask` re-reads the user).                    | partial — sessions carry the role; a per-request user lookup is the next step |
| 2   | The external provider succeeds but we time out before the response | Every outbound write is at-least-once and idempotent on the far side. Stripe calls carry an idempotency key derived from our record (`stripe.service.ts`: `invoice:<id>:create`, `refund:<paymentId>:<amount>:<reason>`), so a retry after a timeout returns the same object. The books have no idempotency key, so `AccountingService` first looks the document up by our DocNumber (`findInvoiceByDocNumber`, `findCreditByDocNumber`) and creates only when absent; a timed-out create is found on the retry and linked, not duplicated. Each attempt is a `SyncAttempt` row with the remote request id. The job that carried it is a `JobRecord` with attempts and a dead letter at exhaustion. | built                                                                         |
| 3   | Two operators approve the same proposal                            | `ProposalsService.claim` takes `SELECT … FOR UPDATE` on the row for the length of the deciding transaction. The second click waits, finds the row already decided and receives 409 `ALREADY_DECIDED`; nothing runs twice, and the audit row names the one who decided. The same lock serves approve and decline.                                                                                                                                                                                                                                                                                                                                                                                    | built                                                                         |
| 4   | A browser disconnects immediately after approval                   | The approval is one API transaction: the decision, the request it creates, the outbox event and the audit row commit together, or not at all. The browser's fate after the POST changes nothing. Its next render (`router.refresh`, a reload, the decision's own page) reads the row as decided; the ledger shows who and when. If the response was lost before it arrived, a second click gets 409 `ALREADY_DECIDED` (see 3) rather than a second run.                                                                                                                                                                                                                                             | built                                                                         |
| 5   | The model provider disappears mid-run                              | Provider calls carry timeouts (`ModelPort`: 120–180 s) and a lost provider surfaces as an error event on the stream; the person sees it, and nothing is half-written: the answer, its tool calls and any proposal are persisted only at the graph's `persist` stage, so a run that fails earlier leaves no message and no proposal. Which provider answers is decided at boot (`AskService`: Anthropic, a local Ollama model, an OpenAI-compatible endpoint, or the deterministic offline answerer), and the status page and the film's page say which. What the build does **not** do is fall back to the deterministic answerer inside a failing run.                                             | partial — fail loud, no half state; mid-run fallback is a next step           |
| 6   | An SSE client misses an event                                      | Events are a courtesy; the server render is the truth. Every page that listens (`useLiveRefresh`) refreshes on a matching event, and since this pass also on reconnect after a drop, so what was missed is read from the database rather than replayed. The bus is in-process and keeps a bounded history (`?replay=N`, used by the lab's live view) that a restart empties. Nothing operational depends on delivery: the consumers that move state run off the outbox and the job ledger, not off the browser stream.                                                                                                                                                                              | built                                                                         |
| 7   | The process restarts with paused decisions                         | A proposal pauses its review thread as a LangGraph checkpoint in Postgres (`ask_graph` schema, `PostgresSaver`); the pause is a row, not memory. A person's decision, hours later on any process, resumes the thread through `ProposalDecided` → `resume(threadId, decision)`. When the checkpoint tables are unavailable the graph falls back to a memory saver and the status page says `durable: false`; the decision itself never depends on the thread — it is the `Proposal` row, decided and audited, and an unknown or finished thread is ignored (`not_waiting`).                                                                                                                          | built                                                                         |
| 8   | Clocks or timezones cross a breeding cutoff                        | Rules never read the wall clock. Every cutoff — the 14-day check, the day-24 heartbeat, departure within 3 days, settlement by Monday — is a pure function over a `BarnDate`, the calendar date at the barn (`barnDate(instant)` in `packages/domain/time.ts`, America/Chicago), supplied by `ClockService` once per request. A server in UTC or a laptop in another zone computes the same barn date; `DEMO_CLOCK` freezes it for the synthetic world. A cutoff that turns over at midnight at the barn turns over once, at the barn's midnight.                                                                                                                                                   | built                                                                         |
| 9   | A secret rotates                                                   | `AUTH_SECRET` is shared by the web app (mints) and the API (verifies), both validated at boot (`env.ts`). Rotating it is a coordinated restart of both; per-request tokens live 2 minutes, so nothing long-lived is signed with it, and existing sessions are invalidated — people sign in again. `STRIPE_WEBHOOK_SECRET` is read on every `constructEvent`; a rotated secret rejects deliveries signed with the old one and Stripe retries, so the write-once inbox (`IntegrationEvent`, unique on provider + externalId) sees each event once. Model and books credentials are read at boot; a rotated key is a restart. There is no dual-secret window.                                          | partial — rotation is a restart, not a rolling handover                       |

## What this table does not claim

It does not claim production hardening beyond what runs here: there is one API process in the
demo, the bus is in-process, and the checkpointer is only as durable as the database beside it.
Every "gap" above is a change to `apps/api`, which this presentation pass left frozen on purpose.
