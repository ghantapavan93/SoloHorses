# AI build ledger

How Claude Code was used to build this, what it got wrong, and what a person had to decide. Kept because the role asks how AI fits into the workflow — and because "AI wrote it" is only reassuring if someone reviewed it.

Commit ids in the rows below point into the working history this repository was built in, day by
day; the published history is organised by layer, so the ids are the record's own references, not
links.

## Four decisions, in short

The long table below is the record. These four are the shape of it: what the agent proposed, what a person decided, and why.

1. **The Stripe duplicate.** The agent's first webhook handler looked a payment up by intent id and updated it — a redelivery would have written twice under load. Rejected: a write-once inbox unique on (provider, external id), the handler counting duplicates instead of processing them, and a test named for the claim, `duplicate_event_creates_one_payment`. The lab's "deliver it again" control exists because that test does.
2. **The papers.** The agent proposed releasing the registration document when the ACH cleared. Rejected: the rule finds the papers _eligible_; a person releases them, by name, on an audit row. When this pass made the ACH return real, that decision paid for itself — a returned debit re-holds an eligible document, and a document already gone out becomes a critical exception, because software cannot recall paper.
3. **The assistant's memory.** The agent's memory store accepted any key and value. Rejected: memory takes preferences — how to say things, what to show first — and refuses facts, money and policy in code (`screenMemory`), so a person cannot accidentally teach it that an invoice is paid. Facts live in records; the assistant reads them fresh every time.
4. **The review graph.** The agent drafted a LangGraph that decided: a node that would approve a proposal when the rule passed. Rejected: the graph orchestrates and pauses; the person's decision is a domain event that resumes it, executed by the same rule-checked service the UI calls. There is one graph in the product, and it never decides.

## Process

1. **Research before code (day 1).** Seven parallel research agents, each told to act as a critic of the incoming plan: the operation's public workflows; the founder's public statements and the job postings; an audit of existing repositories for reuse; live verification of every dependency version and license; Stripe and QuickBooks current API shapes; the Anthropic SDK's current API and an eval design; the operation's measured brand palette and ops-UI density references. Then one critic agent read all seven and ranked seventeen reasons the plan would be rejected. Reports are in `docs/research/`.
2. **The plan changed because of the research.** The incoming plan had NestJS/Redis/QuickBooks on faith, an approval-gated "propose action" assistant, a candidate landing page with a card-fold animation, a 3D ranch topology, and an Eval Lab page. Research showed the public posting listed a different stack (later superseded by the actual job description, which named NestJS/Prisma/Redis/BullMQ and QuickBooks explicitly — see ADR-001), that the founder already ships a customer portal with an assistant, that ICSI happens at an outside lab, that billing fires on clinical milestones, and that embryo intake is literally a text message. The landing page, fold, and 3D were cut; the Day Sheet became a collection/transfer manifest; intake by SMS was added; the approval gate became a read-only assistant with "Send to team".
3. **Then code, in this order:** domain rules with tests → schema and seed → API modules with integration tests → the web harness → e2e → docs.
